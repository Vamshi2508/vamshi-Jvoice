3. Cross-App Findings

Individually, the web and Android audits (see web.html / android.html) each flagged real bugs. Comparing them against each other surfaces the most important finding for planning enhancements:

★ Study content authored on the web console never reaches the Android app

The web console's Study pages (Subjects, Topics, Study Material, Question Bank, Exams) are already Firestore-backed — content a Content Creator publishes there is written live to subjects/topics/studyArticles/questions/exams in Firestore. But the Android app's Study module (StudyRepository, ExamTrackRepository) still reads exclusively from MockDataSource and never queries Firestore, even though the matching codecs (StudyCodec.kt) and collection names already exist on the Android side.

Practical effect: a Content Creator can publish new study material or questions through the web console all day — students in the Android app will never see it. The News module went through exactly this migration already (web ↔ Android both read/write the same Firestore articles collection); Study has the schema in place but the Android read-side wiring was never finished.

Both apps' top-level docs are stale in the same way

Web's README.md/ACTIONS.md and Android's README.md/SCREENS.md all independently claim "no backend, no Firebase, no real auth" — all four are describing an earlier prototype. Both apps have since gained real Firebase Auth/RTDB, and the News module on both sides is Firestore-backed. Worth a documentation pass once the enhancement work below is scoped, so the docs don't keep misleading new contributors.

AI Shorts exists — fully — on both platforms, both fully mocked

Web's Shorts.jsx and Android's 12-file aishorts/ module both implement a complete news→short-video pipeline UI with zero real AI/TTS/render backend behind either. This is consistent between platforms (good), but represents the largest single "fake" surface in the product if AI Shorts is meant to ship for real.

Security rules are the one place already built for the full role set

web/firebase/firestore.rules and database.rules.json already validate against all ten desk roles (reporter, editor, news_admin, content_creator, exam_admin, study_admin, super_admin, ...) via custom claims — this part of the backend is ahead of both clients, not behind them, and can absorb the Android Study migration without rule changes.

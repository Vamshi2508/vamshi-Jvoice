1. Overview & Purpose

⚠ README.md / SCREENS.md are stale

Both open with "Everything runs on local dummy/mock data. There is no Firebase, no backend, no API, no real authentication..." — false for the current source tree. Treat this document, not those files, as the source of truth for current state.

Two modules, switchable at runtime by an authorized user:

Module 1 — News

District/regional news workflow: reporters file stories, editors review/publish, admins moderate. Public-facing reader: flip-card feed, short clips, search, categories.

Module 2 — Study & Exam Prep

Competitive government-exam prep (Police Constable, SI, Group-1/2/4, VRO, SSC, RRB, Bank, DSC) — syllabus content, quizzes, timed tests, leaderboards, performance analytics.

The web app is the desk/admin console for both modules; this Android app serves the public reader/student audience directly, and — via a newly added staff login — the same desk roles as the web console, sharing one Firebase project.

2. Tech Stack

Language & UI

  • 100% Kotlin — no Java, no XML layouts, pure Jetpack Compose (Material3)
  • MVVM-ish: singleton repositories (StateFlow) as source of truth, thin ViewModels, composables read flows directly
  • No DI framework (no Hilt/Koin) — manual Kotlin object singletons
  • compileSdk/targetSdk 36, minSdk 24 (bumped 34→36 for Play Store)

Key libraries

  • Compose BOM 2024.06.00, navigation-compose 2.7.7
  • coil-compose 2.6.0 (image loading)
  • firebase-bom 33.1.2 → Auth, Realtime Database, Firestore
  • kotlinx-coroutines-play-services (Task↔coroutine adapters)
  • AGP 8.9.1, Kotlin 1.9.24, Gradle 8.11.1, JDK 17

Firebase wiring is conditional: build.gradle.kts applies the google-services plugin only if app/google-services.json exists, mirrored into BuildConfig.HAS_FIREBASE_CONFIG so Gradle-time and runtime never disagree.

4. Backend Integration

Two backends coexist at different maturity levels — both pointed at the same Firebase project (jvoice-b4b2e) the web console uses:

News module — real backend

  • Firestore: articles, categories, newsNotifications, articleReports, live addSnapshotListener
  • Anonymous readers get a status-filtered query (required to satisfy Firestore security rules)
  • Writes are fire-and-forget — Firestore's offline cache + queued writes handle connectivity gaps ("usable for a reporter filing from a village with no signal")

Study module — still mock

  • StudyCodec.kt + target Firestore collection names (SUBJECTS, TOPICS, EXAM_TRACKS, STUDY_ARTICLES, QUESTIONS, QUIZZES, EXAMS) are fully defined
  • But StudyRepository.kt/ExamTrackRepository.kt still initialize every StateFlow from MockDataSource and never touch Firestore
  • Only consumer of the codecs today: a debug-only one-off export path (DevExport.kt → web/firebase/seed-content.mjs)

Realtime Database holds users/{uid} (role, isLogin kill-switch, forceLogoutAt, lastLoginAt, per-account update gate), top-level /flags (remote feature flags — same ones the web Feature Flags page writes), /failedLoginAttempts, /passwordResetRequests.

Study module session ignores real sign-in

StudySessionViewModel.signInAs(role) always sets MockDataSource.demoAccounts[role] — it never reads SessionStore, unlike the News module's equivalent. A real Firebase-authenticated Content Creator / Exam Admin / Study Admin / Super Admin entering the Study module is shown as a canned demo persona, not their real identity.

6. State Management & Data Flow

  • Every repository is a Kotlin object singleton exposing MutableStateFlow/StateFlow — no Room/SQLite anywhere.
  • News: UI → repository function → Firestore.set/update/delete (fire-and-forget) → attached listener echoes the change back into the StateFlow → Compose recomposes. Firestore persistence configured with unlimited cache size.
  • Study: pure in-memory — every mutation does a direct _stateFlow.update{} with no external persistence; state resets on process death.
  • Local-only device state: ReadStateRepository, LanguagePreference, SessionStore (SharedPreferences, jvoice_desk_session).
  • Live RTDB signals: FeatureFlags and ForceLogoutGuard both "fail open" by design (missing/unreadable data → treated as enabled/no-op) — a deliberate documented safety choice.

8. Known Issues & Risks

google-services.json committed to the repository

Contains a real project id, RTDB URL and API key for jvoice-b4b2e. Typically restricted by package name/SHA-1 rather than a bearer secret, but committing it means anyone with repo access can build against the live production backend. .gitignore protects signing material (*.jks, keystore.properties) but has no equivalent rule for this file — worth a deliberate decision.

android/app/google-services.json

Release build is prepared but cannot actually be signed from this checkout

Commit f811f57 ("Prepare the Android app for a Play Store release build") correctly bumped compileSdk/targetSdk 34→36, AGP/Gradle versions, versionName to 1.0.0, added conditional release-signing keyed on a gitignored keystore.properties, and enabled minify/shrink with real ProGuard keep rules. But no keystore.properties or .jks exists in this checkout (by design — gitignored) — so canSignRelease evaluates false here, and a release build from a fresh clone is unsigned. Whoever owns the keystore must supply it out-of-band.

android/app/build.gradle.kts, android/app/proguard-rules.pro

Clips tab silently non-functional

ClipsRepository._clips starts as an empty MutableStateFlow with no path anywhere that populates it. The Clips tab shows its empty state on every launch — a regression beyond what SCREENS.md's own "known limitations" section discloses.

news/data/repository/ClipsRepository.kt, ui/.../VideoClipsScreen.kt

Study desk-identity bug may misattribute authorship

Because a real Firebase-authenticated Content Creator/Exam Admin/Study Admin/Super Admin is shown as a demo persona inside the Study module, content-authorship fields (e.g. authorName) written from that session could be wrong.

study/ui/auth/StudySessionViewModel.kt

Stale KDoc comments

SessionViewModel.kt's class doc ("Dummy session holder, no real authentication") is wrong for desk roles now that NewsRepository.signInAs threads through SessionStore. The equivalent comment on StudySessionViewModel.kt happens to still be accurate, since that migration hasn't landed.

DevExport runs on every debug launch

MainActivity.onCreate unconditionally calls DevExport.exportIfNeeded() (guarded by BuildConfig.DEBUG, so it can't run in release). Writes a full JSON dump of Study content to external files on every debug install. Both DevExport.kt and SeedExportTest.kt say in their own KDoc this is temporary and should be deleted once the Study→Firestore migration lands — it hasn't been.

core/data/DevExport.kt, app/src/test/.../SeedExportTest.kt

Security rules are a real strength, but tightly coupled across the monorepo

Role comes from a Firebase custom claim for Firestore; RTDB rules correctly restrict users/ writes to super_admin. But the rules live in web/firebase/, not alongside the Android code — any change to JvRole codes must stay in lockstep with both rule files, which is a discoverability risk for anyone working only in android/.

web/firebase/firestore.rules, database.rules.json vs android/.../core/auth/JvRole.kt
